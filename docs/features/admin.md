# Setup, administration and operations

This map covers everything an administrator does with Gunmetal other than
listening and watching: installing it, the first run, moving in from Plex,
Jellyfin, Emby or Navidrome, upgrading and rolling back, backing up and
restoring, keeping the database healthy, looking after the folders the
library lives in, scheduled work, the admin dashboard and activity log,
alerts, logs and diagnostics, and the security operations around them (keys,
the audit log, exposure). Sign-in design, user policy, invitations,
library scanning rules and webhooks have their own feature maps; they appear
here only where they change an operational task. The bar is this: a family
admin can install Gunmetal on a small box in minutes without creating an
account anywhere; no upgrade, corrupt database or NAS outage can lose
anything that cannot be rebuilt from the files; history, ratings and
playlists come across from the old server with a report before anything is
written; no admin screen shows one adult what another adult played; and the
tools people run beside Plex and Jellyfin today (Tautulli,
PlexDBRepair, WatchState) become optional. Everything Plex and Emby charge
for in this area is free. Where rivals are already good (Immich's backups and
restore from the welcome screen, Jellyfin's pre-migration copy and startup
page, Navidrome's small command-line toolset and single binary, Plex's
maintenance window and phone dashboards, Emby's packaging breadth) the aim is
parity first and an edge only where the architecture provides one.

## Features

Conventions used in the tables:

- Releases (R1, R2, R3, Later, No), the Demand scale, row ownership and the
  terms "the user log" and "the identity store" are defined once in the
  [feature map README](README.md). A row whose Release cell would differ
  between maps names one owning row; the other maps point at it. ADR 1 (decision 5)
  makes only watch history durable, so every row that stores other user
  state depends on ADR 3 (see Dependencies and risks).
- UI surfaces are named as screens: the first-run flow is "Welcome", the
  admin area is "Admin > ...", the minimal server-rendered page is the
  "Emergency page", and the page shown before the database opens is the
  "Startup page". "CLI" means a `gunmetal` subcommand on the host.
- Rival evidence comes from the research files in `docs/research/`. Vote
  counts are as read on 2026-10-02. "(unverified)" marks claims the research
  could not confirm.
- The Security column lists the requirements in the
  [security baseline](../security/README.md) that a builder must satisfy for
  the row. Where this map and the baseline disagreed, the row now follows the
  baseline (review of 2026-10-02), and the baseline wins any disagreement
  that remains. "None (not built)" marks rows that will not be built.
- "The owner" is the one person who claimed the server; administrators
  cannot do what is marked owner-only. "A fresh passkey check" means user
  verification within the last 5 minutes (SEC-IAM-041). Owner-only and
  fresh-check actions are those listed in SEC-TM-017 and SEC-IAM-041.

## Differentiators

1. **Backups that are tiny, daily, encrypted and free, with restore from
   the welcome screen** (ADM-065, ADM-068, ADM-072, ADM-029 and the recovery
   kit, ADM-143, all in R1). Plex backs up only its core
   database every three days and leaves out settings; Jellyfin's backups are
   manual and its scheduling request has 91 votes; Emby charges for them.
   Because Gunmetal's database is a rebuildable cache, the backup is only the
   user log, settings, identities, the audit log and keys, so it can run
   daily by default, be encrypted and signed, be verified after every run
   and be restored on a fresh install in minutes. A stolen copy is useless
   without the owner's recovery kit.
   This is the clearest answer to the Plex backup and move complaints.
2. **Upgrades that can always be undone** (ADM-056, ADM-057, ADM-058,
   ADM-059, ADM-060). Plex's 1.43.0 packaging failure, Jellyfin's 10.11
   migration failures and Immich's refusal to downgrade show that every rival
   treats an upgrade as one-way. Gunmetal snapshots before migrating, can
   check a migration before serving, never lets a migration loosen a
   security setting, and lets an older binary rebuild its cache from the
   files and log, or point to the snapshot when it cannot read newer data.
   Admins who were burned by an upgrade will notice.
3. **Moving in from Plex, Jellyfin, Emby or Navidrome is built in, with a
   dry run and undo** (ADM-036 to ADM-046, ADM-051). Today this takes
   WatchState, JellyPlex-Watched or one-off scripts, and Plex's own sync
   leaves out music. Reading offline database copies needs no account on the
   old server, and every imported fact can be backed out. History lands with
   the person it belongs to, never in front of the admin. Switching cost is
   what keeps lifetime Plex Pass holders in place. R1 ships the file-based
   importers (M3U playlists, Last.fm and ListenBrainz exports, ADM-042 to
   ADM-044), each person importing their own. iTunes files, the dry run and
   undo (ADM-041, ADM-045, ADM-046) arrive in R2. The readers for rival
   databases (ADM-036 to ADM-040, ADM-047 to ADM-049) come Later, because
   each rival schema has several versions to support, each database copy is
   hostile input that must be read in a jailed worker, and the threat
   model's release scope puts them there.
4. **A free dashboard that explains every stream** (ADM-099, ADM-100 and
   ADM-102 in R1; ADM-101, ADM-103 and ADM-106 in R2). Plex puts everything past "now playing"
   behind Plex Pass; Jellyfin users have asked for years to stop a stream
   (402 votes), and Plex users to message everyone (1,206 votes); Tautulli
   and Jellystat exist to fill the gap. Gunmetal shows the playback decision
   and its reason for each session, stops streams for real and computes
   totals from the log it already keeps, without showing any admin what
   another adult played. The direct-play breakdown also
   proves the project's main claim to every admin who opens the page.
5. **Nothing to repair** (ADM-077, ADM-079, ADM-080, ADM-123). PlexDBRepair's
   1,228-post forum thread and Jellyfin's 229-comment "database is locked"
   issue are symptoms of databases that hold irreplaceable data and are
   written from many places. Gunmetal keeps one writer, refuses network
   filesystems for its data, and fixes a bad cache by rebuilding it, with
   `gunmetal doctor` in place of third-party repair tools.
6. **A NAS outage never empties the library, and scans do not hammer
   shares** (LIB-032, which ADM-085 points to, and ADM-088; per-root I/O
   profiles, ADM-087, in R2). Jellyfin's docs warn that tasks can
   remove items while storage is offline, and Plex scans have exhausted cloud
   drive quotas. Gunmetal treats a missing root as offline, never as deleted,
   and its scans read headers only and report the bytes they read.
7. **You own it from the first second** (ACC-001, ACC-002, ADM-028,
   ADM-053, ADM-142). No vendor account, a setup code that stops anyone else
   claiming the server, no password to steal, nothing contacting the
   internet that the owner did not choose, and a security summary that says
   how the server is exposed. Plex's local-authentication request (372 votes)
   and its July 2026 outage are the contrast.

## Deliberately not doing

- **External database engines (ADM-084).** SQLite is a rebuildable cache
  with one writer. Jellyfin's 663-vote MySQL request mostly reflects locking
  and corruption pain that this design is meant to remove, and a second
  engine would double the surface held to the coverage and mutation gate.
- **Copying or syncing media between servers or drives (ADM-092).** Gunmetal
  reads media and does not manage it; general file tools do this better, and
  read-only media is a security property worth keeping.
- **Telemetry on by default (ADM-136).** Nothing leaves the server unless
  the owner chose it.
- **Crash reports sent to the project (ADM-131).** A project service that
  collected them would hold data about people's servers. Crash records go
  into the diagnostic bundle (ADM-124), which the admin can attach to a
  report themselves.
- **Running as root, even with an override (ADM-006).** The server refuses
  to start as root or with any capability.
- **Writing into media folders (ADM-089, ADM-139).** No sidecars, no tag
  writing and no deletions; removing a file from disk is the owner's job.
- **Admin views of another adult's history (ADM-099, ADM-106).** Admins see
  live sessions without titles unless each person opts in, and totals.
- **Edge or caching servers (ADM-138).** Little demand, and offline sync
  covers the travel case.
- **Container tags that download a server at start.** The image you pull is
  the version you run (ADM-003).
- **A server that updates itself.** The server never writes its own binary;
  automatic updates come only from the package manager or a container tool,
  and are opt-in (ADM-064).
- **A project kill switch.** Emby stopped compromised servers from starting
  in 2023. Gunmetal's project will never be able to disable someone's server
  remotely; the advisory banner (ADM-054) is the only channel.
- **Emailing owners about security problems.** Plex can do this because it
  has accounts. Gunmetal has none and will not add them for this; the signed
  feed and banner replace it.
- **A "trust the local network" admin sign-in, setup without a code, or a
  password fallback at setup (ADM-019, ADM-021).** Passwordless local admin
  access combined with forged headers is how Emby servers were compromised
  in 2023, and a password over plain HTTP can be read by anyone on the
  network.
- **Packages that block downgrades.** Rollback depends on being able to
  install the previous version (ADM-016, ADM-059).
- **Flatpak and Snap packages for the server.** Emby offers them, but the
  container image and native packages cover the same machines, and there is
  no demand evidence for them in the research.

## Dependencies and risks

- **Blocking: ADR 3, durable user state.** ADR 1 (decision 5) names watch
  history as the only irreplaceable data, but most rows in this map that
  write user data (playlists, loves, ratings, corrections, layouts, shares,
  identities, IDs, settings) need it to survive a cache rebuild. ADR 3 must
  be accepted before any server work that stores user data. It defines the
  two durable stores every map now names the same way: **the user log** and
  **the identity store** (see the [feature map README](README.md)).
- **A new ADR on durable state is a precondition.** ADR 1 names watch history
  as the only irreplaceable data. Small backups (ADM-065), rebuild instead of
  repair (ADM-077), rollback (ADM-059) and undoable imports (ADM-046) are
  only true if ratings, playlists, curation, users, passkey public keys,
  device keys, sharing grants, settings, certificates and server identity
  keys also live outside the SQLite cache. If any of them ends up only in
  SQLite, these features quietly become false.
- **First-run on a LAN address needs an ADR of its own.** WebAuthn needs a
  secure context and a domain, not an IP address. R1 has only a web client,
  so the most common setup (a headless box reached by IP) cannot register a
  passkey without one of: localhost, the admin's own domain (ADM-022), a
  tailnet name, or the project name service (ADM-023). The security baseline
  rules out the weaker fallbacks: no passwords (SEC-IAM-025) and nothing
  over plain HTTP (SEC-NET-001). How easy R1 setup is therefore depends on
  the name service, its Public Suffix List entry and an ADR amending ADR 1
  decisions 7 and 9. Native-app enrolment (ADM-035) helps only from R2. The
  baseline reports that Chrome refuses WebAuthn on pages with certificate
  errors, so a self-signed certificate does not help.
- **Log format discipline.** Rollback by starting an older binary assumes
  the log only grows by new, versioned event types, and only types marked
  safe to skip may be skipped. Some new event types, such as import
  retractions, change meaning when ignored; an older version that meets one
  must refuse to start and point to the snapshot (ADM-059) rather than show
  undone imports again. Release notes must say this plainly (ADM-060), and
  some releases will not be safe to roll back past.
- **Rebuild time is the price of a rebuildable cache.** A restore or
  rollback means a rescan. That is quick for music but could take hours for
  a large video library on network storage. The scan benchmark must report
  rebuild time, and the optional cache snapshot (ADM-067) is the fallback.
- **Importers read undocumented schemas.** Plex, Jellyfin, Emby and
  Navidrome can change their databases in any release (Jellyfin twice in a
  year; Navidrome re-encoded every ID in 0.64). Importers need fixtures from
  many versions and must read copies, never a running server's live files,
  and every copy is hostile input read only in a jailed worker
  (SEC-STD-031).
- **Content identity belongs to the library map.** Matching imports, keeping
  history across renames and the integrity report all depend on the file
  identity the library map defines. A wrong match silently moves someone's
  history onto the wrong file.
- **Folder browsing at setup is an attack surface.** Jellyfin published a
  critical path-traversal advisory in library-folder management in
  September 2026. The picker in ADM-025 must be admin-only, need a fresh
  passkey check, list directories only within configured browse roots
  (SEC-API-022), and be covered by the route-authorisation tests.
- **Alerts and webhooks share plumbing with the integrations map.** An
  owner-granted alert destination may be one exact LAN host, while plugin
  traffic to the LAN is blocked by default; the two rules must be different
  and visible.
- **What the dashboard shows about other users is set by the security
  baseline.** Live sessions without titles unless each person opts in,
  totals, and no per-person history (SEC-PRV-025). Session detail and
  statistics (ADM-099, ADM-106, ADM-126) follow it, and the accounts map's
  "choose what admins see" setting must not offer a full-history option.
- **Music playback decisions depend on the music map.** The security
  baseline recommends no transcoding in R1 (Opus arrives with the jail in
  R2), so the "no FFmpeg for music" statement in ADM-001 holds for R1.
- **The project name service is a dependency the project runs.** It must
  hold only labels and public keys, launch only after its zone is on the
  Public Suffix List, and fail without breaking any other path (ADM-023).
- **The transcode sandbox varies by kernel.** Some NAS kernels are old. When
  the sandbox cannot start, transcoding is off and says why (ADM-133), which
  may surprise people who expect Plex-like behaviour.
- **Without telemetry the project is blind.** It will not know which
  versions are deployed or which upgrades fail. The update check sends
  nothing about the server and no crash reports reach the project, so
  release testing, and the diagnostic bundles people choose to attach to
  reports, have to carry more weight.
- **Packaging is a long tail.** Every OS, package repository and NAS catalog
  has its own signing and review rules; Plex's January 2026 signing failure
  shows a large company getting it wrong. Each target added is a target
  tested on every release.
- **SQLite still needs care.** One writer removes internal lock contention,
  but long transactions during scans can still stall readers, and
  environment-specific problems (ZFS, LXC) are hard to reproduce. Load tests
  have to cover them.
- **Release signing keys become critical infrastructure.** The update feed,
  advisory banner, container tags and package repositories all rest on
  them. The feed's root and advisory roles are signed with offline hardware
  keys held by different people (SEC-SUP-049).
- **The release-scope table in the threat model decides what exists when.**
  Rows here follow it (SEC-TM-074): Linux servers only in R1, rival
  database importers and email alerts Later. Moving any of them earlier
  means changing that table first.

## Open decisions for the project owner

1. **Which user state is irreplaceable, and how is it stored?** Recommendation:
   write the durable-state ADR before the server's data model. Treat as
   durable everything a rescan cannot recreate (watch and listen history,
   ratings, playlists, curation, users, credentials' public keys, device
   keys, grants, settings, certificates, server identity), stored as typed
   streams in one log format with one backup, export and replay path.
2. **How does R1 let a browser register a passkey on a server reached by IP
   address?** Options were localhost only, the admin's own domain, a
   project name service (like plex.direct), or a password fallback. The
   security baseline settles most of this (its open decisions 1 and 2):
   there is no password fallback, and plain HTTP serves only a help page.
   Recommendation, owner to confirm: run the project name service in R1 as
   the install-time default (ADM-023), launched only once its zone is on the
   Public Suffix List, with own-domain HTTPS through ACME (ADM-022), tailnet
   names and localhost as tested alternatives; if the Public Suffix List
   entry is not in place, R1 ships with the alternatives only. The name
   service conflicts with ADR 1 decision 7 (no central account) and
   decision 9 (Cloudflare hosts only the docs and landing page), so an ADR
   amending them must come first. Some routers block DNS names that resolve
   to private addresses (unverified), which the alternatives cover.
3. **Is the update check opt-in or opt-out?** Settled by the security
   baseline (SEC-OPS-047; its open decision 4, owner to confirm): a required
   question at setup with two explicit answers and nothing preselected,
   plus a plain statement that the request carries no identifiers but that
   the host serving the feed sees the requesting address. The advisory
   banner depends on it, which is argument enough for most admins to say
   yes.
4. **No telemetry at all, or opt-in crash reports?** Recommendation (the
   security baseline's open decision 24, owner to confirm): no usage
   telemetry and no crash reports sent to the project, ever. ADM-131 is now
   "No"; crash records go into the diagnostic bundle (ADM-124), which the
   admin can attach to a report.
5. **What ships at R1 for installation?** Recommendation, following the
   security baseline's open decisions 10 and 14 (owner to confirm): static
   binaries for Linux (x86-64, AArch64) plus the container image in R1,
   with systemd integration only (ADM-005), and a server that refuses to
   run as root with no override (ADM-006). macOS and Windows server builds
   and their installers in R2 only once their worker sandbox profiles exist
   (SEC-MED-082); Docker Desktop covers those machines until then. ARMv7 in
   R2 only once wasmtime support and the worker's seccomp answer are
   settled (ADM-004). Signed deb and rpm repositories and NAS catalog
   templates in R2. FreeBSD and native NAS vendor packages Later.
6. **Which importers ship at R1, and how do they read data?** R1 imports
   only M3U playlists and Last.fm and ListenBrainz export files, each
   person importing their own. iTunes files, the dry run and undo come in
   R2. The threat model's release scope puts importers for rival databases
   at Later, so the Plex, Jellyfin, Emby and Navidrome database readers,
   the API path and the user and side-by-side imports (ADM-036 to ADM-040,
   ADM-047 to ADM-049) are Later; moving them earlier means changing that
   table first. Every database copy is read in a jailed worker
   (SEC-STD-031), and reading over a rival's API needs an owner grant for
   one host and an egress inventory row. Reading another product's
   database format for interoperability, and naming those products in the
   import screens, is believed to be acceptable (unverified; this is not
   legal advice and should be checked once).
7. **What can an admin see about other users by default?** Settled by the
   security baseline (SEC-PRV-025; its open decision 5, owner to confirm):
   live sessions with person, device, bitrate and playback method, the
   title only when that person opts in, aggregate totals, and the security
   log with other people's addresses shortened; no per-person history, no
   household option to turn it on, and every user can see what the admin
   can see. Guardians of managed child profiles (R2) are the exception.
8. **Where does the admin dashboard live?** Recommendation: the full
   dashboard in the React Native client, so it reaches phones and tablets
   in R2 (never TVs, which cannot hold admin rights), plus the minimal
   server-rendered emergency page (ADM-113), behind its own passkey
   sign-in, for when the client is broken.
9. **What rollback guarantee does the project make?** Recommendation:
   upgrading from any older version always works (ADM-058). Rolling back is
   guaranteed to the previous minor version and stated for every release
   (ADM-060); an older binary that cannot read newer durable data refuses
   to start and points to the snapshot (ADM-059). Never ship a package that
   blocks a downgrade.
10. **Confirm that external database engines are out (ADM-084).**
    Recommendation: confirm "No" for R1 to R3 and revisit only if large
    multi-user installs show SQLite limits that one writer and a rebuildable
    cache do not solve.
11. **Are off-site backup destinations part of the server or a plugin?**
    Recommendation: in the server from R2, limited to S3-compatible storage
    and WebDAV, always encrypted and added only by the owner, because
    backups are core to the project's promises. The egress inventory needs
    a row for them first. Other destinations can be plugins.
12. **Who holds the release signing keys?** Recommendation, as the security
    baseline sets it (SEC-SUP-049): TUF metadata whose root, release and
    advisory roles are signed with offline hardware keys held by different
    people (threshold 2 once two keyholders exist), only snapshot and
    timestamp signed online, and a published rotation and compromise
    procedure, rehearsed yearly, before R1 ships.
13. **Confirm the other changes made to follow the security baseline.**
    These rows changed to match the baseline's recommendations on the
    owner's open security decisions, and each needs the owner's yes: the
    server name hidden before sign-in (ADM-140; web OD-5 in the baseline's
    smaller choices); media never written to, with removal left to the
    owner's own tools (ADM-089, ADM-139; decision 23); retention defaults in
    R1 (ADM-111; decision 15); automatic updates only through the package
    manager or a container tool (ADM-064; decision 25); and email alerts
    moved to Later (ADM-116; decision 25).

## Security notes

This area crosses more trust boundaries than any other: TB1 and TB2 (setup,
the admin surface and the emergency page are reached over the network), TB8
(the update feed, the name service, ACME, providers and alert
destinations), TB9 and TB10 (media roots, the data directory, backups,
snapshots and logs), TB11 (the step from member to administrator to owner
to the host) and TB12 (releases, packages and the feed). The threats from
the [threat model](../security/threat-model.md) that matter most here, and
how the rows above answer them:

| Threat | What it would look like here | How this map answers it |
|---|---|---|
| TM-T06: someone claims a fresh server first | A neighbour or a web page reaches the welcome screen before the owner, or restores their own backup onto it | The setup code from the console, accepted only over loopback or HTTPS (ADM-018); setup gone for good, with a locked state instead of a reopened wizard (ADM-020); restore at setup behind the same code (ADM-029); nothing seeded from config can make anyone owner (ADM-024) |
| TM-T11, TM-T46: credentials over cleartext | A password or session typed at an IP address over plain HTTP | No password fallback (ADM-019); plain HTTP serves only a help page (ADM-021); HTTPS through the name service, the owner's domain, a tailnet or localhost (ADM-022, ADM-023) |
| TM-T05, TM-T48: "local" treated as trusted | A port forward or tunnel makes internet requests look local and reach admin pages | Proxies trusted only when the owner declares them (ADM-022); admin routes refused on internet-facing paths unless remote administration is on (ADM-113); exposure shown and alerted (ADM-142, ADM-116); one address classifier for logs and limits (ADM-104, ADM-122) |
| TM-T18: history disclosed to admins | Now playing, statistics, imports, exports or traces show one adult what another played | Live sessions without titles unless each person opts in (ADM-099); totals only (ADM-101, ADM-106); importers that show counts and library items, with history attaching to its owner (ADM-036 to ADM-049); per-person exports (ADM-074); traces without titles and logged to the subject (ADM-126) |
| TM-T54, TM-T55: owner access becomes host access | The server runs as root, or a setting points at a program | No root and no capabilities, with no override (ADM-006); hardened unit, image and templates (ADM-002, ADM-005, ADM-015); no config key takes a program or command (ADM-007); no self-update (ADM-064); no wake privileges (ADM-098) |
| TM-T56, TM-T25: the media collection damaged or escaped | A bug, an intruder or an offline share deletes or rewrites files; a symlink or folder picker reaches the secrets | Media read-only, always (ADM-089, ADM-139); offline roots never delete (ADM-085); the folder picker confined and refusing the data directory (ADM-025) |
| TM-T57, TM-T59: secrets and backups leak | A backup copied to a cloud drive, a support bundle or a log line holds history, keys or tokens | Every backup encrypted and signed (ADM-065, ADM-068) with a recovery kit (ADM-143); owner-only downloads (ADM-069); pseudonymised bundles (ADM-124); secrets that cannot reach logs (ADM-121); one-action key rotation (ADM-144) |
| TM-T60: a rebuild or migration fails open | An upgrade, rollback or restore loses restrictions, revocations or settings | Verified snapshots before migrating (ADM-056); no migration loosens a setting (ADM-057, ADM-147); an older binary refuses data it cannot read (ADM-059); restored devices start suspended and keys rotate (ADM-070); restricted items hidden during a rebuild (ADM-077) |
| TM-T61: no trustworthy record | An intruder erases the trail of what they did | A hash-chained audit log nobody can clear (ADM-110), verified against backups and an off-server anchor (ADM-145), and a runbook that starts there (ADM-148) |
| TM-T01, TM-T43, TM-T44: unpatched servers and a hostile update channel | Owners never hear about a fix, or the feed is forged or used as a kill switch | A signed TUF feed asked about at setup (ADM-053) that can only inform (ADM-054); signed, reproducible releases and images (ADM-001, ADM-003); no remote control of any server |
| TM-T33: lookups tell third parties what the household has | Providers, the update check or alert channels learn about the library or its people | Required, explicit privacy questions at setup (ADM-028); one egress client with a visible ledger (ADM-129); proxy and offline modes (ADM-146); content-free alerts (ADM-116); no telemetry or crash reports (ADM-131, ADM-136) |
| TM-T63: a recovery path bypasses sign-in | Owner recovery or a reset is reachable over the network | Owner recovery only through a command on the host (ADM-034); ownership moves only by a transfer both people confirm (ADM-052) |
| TM-T09: resource exhaustion on small hardware | A huge library, a hostile file or a flood stalls the household's music | Analysis in a throttled, jailed queue with quarantine (ADM-095); concurrency limits (ADM-096); one writer (ADM-080); free-space guards (ADM-083) |

Two risks remain whatever the rows say. The owner controls the host and can
read the database directly; the product promises only what it shows, and
each person's "what your admin can see" page says so (ACC-115). And the
project's own signing keys and name service are single points that every
install trusts, which is why they are offline, split between people and
rehearsed (SEC-SUP-049, SEC-OPS-071, SEC-NET-070).
